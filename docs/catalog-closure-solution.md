日期：2026-10-26。状态：方案已形成，功能实施尚未开始。

本方案承接最近一次能力对照，按“电话覆盖 → PCI 关系 → 历史资源来源 → 双平台交付”推进。当前回合交付解决方案；后续按本方案逐项实施和验收。此前功能、未提交修复及历史证据均保留。

## 3. N01：电话全目录覆盖

### 3.1 解决方式

1. 从已固定的 SQLite 与原始 XML 建立“稳定键、地区、呼叫码、类型、模式、来源版本”清单，核对导入遗漏及数量。保持该源版本，先验证已有数据。
2. 保留 `Phone.Number("CN", ...)` 的国家/地区调用。增加明确面向非地理号码区的呼叫码入口，建议签名为 `Phone.NonGeographicNumber("870", PhoneNumberType.Mobile, extension: true)`。
3. 新入口通过独立的可选 Provider 能力解析 `001` 记录，避免给现有 `IPhoneMetadataProvider` 强加必须实现的新成员。仅按呼叫码猜测国家的行为不进入该接口。
4. 对全部导入规则走真实 PhoneData → Provider → 生成器 → 格式化路径。先枚举支持语法，再运行固定记录矩阵；只针对具体失败改动生成或适配逻辑。
5. 修正模式、格式或前缀处理时保留原始来源字段；每条输出仍需匹配原始规则。受控生成不能以删除来源约束来换取成功。
6. 发现来源没有某个地区/类型时继续返回覆盖错误。有效来源规则的生成失败单独记为实现问题或已验证边界，不归入“来源缺失”。

### 3.2 验收与资源

- 两套资产各覆盖当前 492 条规则，每条固定 20 个记录序号；Seed、参考时间和目录版本固定。每套基础矩阵为 9,840 个样本，测试逐条核对并释放，不保存全部号码。
- 验证 ASCII 数字、原始类型模式、呼叫码、E.164 最长 15 位主号码、分机分离、本地格式替换及对应前缀规则；格式规则不存在时保留未格式化号码的语义。
- 固定矩阵覆盖重复枚举、单条重放、串行与并发度 4 一致性。共享呼叫码国家、非地理号码、空格式规则、取消及释放路径另设精准用例。
- 首先使用原有默认长度、步骤与尝试预算；失败记录保留稳定键、记录序号、异常类型及重放身份。不能通过提高默认重试次数掩盖确定性缺陷。
- 全目录固定采样通过代表该矩阵覆盖通过，不宣称穷尽每个正则分支。解析器变更另用针对性分支与极值测试验证。

主要范围：`Data/CommunicationData.cs`、`CatalogPhoneMetadataProvider.cs`、电话集成测试；必要时修改有限正则生成器，并扩大到 AutoBuilder/Schema 的受影响测试。

## 4. N02：PCI 原始快照与关系完整快照

### 4.1 推荐的数据策略

保留 `pci-ids.sqlite3` 原始导入快照，另生成 `pci-ids-resolved.sqlite3`，由需要完整关系的调用方明确挂载。两者从同一固定源生成，具有不同的数据集身份与转换版本。

- 原始快照继续包含全部 42,549 条记录及 46 条缺失引用，保持其审计价值和既有行为。
- 派生快照仅排除无法解析 subvendor 的子系统记录，保持其他记录的稳定键、名称、内容及顺序约定。
- 根据当前缺失情况，派生结果预计为 42,503 条；实际生成需重新全量核对，不能把预期数字直接写成通过证据。
- 保存逐条排除清单：原记录键、缺失目标键、原因、源版本和派生规则版本。验证“派生记录 + 排除记录 = 原始记录”，并验证无额外修改或静默遗漏。
- 不合成不存在的厂商，也不把排除后的目录描述为完整原始 PCI 目录。

### 4.2 接口与门禁

继续使用现有 `UseCatalogFile("devices", path)` 挂载方式，示例明确展示两种路径及覆盖差异；无需增加全局筛选开关或新的常驻缓存。

门禁独立输出：

|检查对象|预期结果|
|---|---|
|原始快照来源一致性|PASS，记录与固定源一致|
|原始快照严格外键完整性|保留 FAIL 及 46 条来源缺失，不改成 PASS|
|派生快照严格外键完整性|PASS，全部保留记录关系可解析|
|派生过程可追溯性|PASS，包含与排除计数闭合，排除原因完整|
|设备模板、确定性、释放|两种挂载分别验证；上下文释放后目录文件可释放句柄|

该方案关闭“需要完整关系的消费路径”欠账；上游原始数据的缺失仍是已验证来源边界。若未来需要原始快照本身外键全部闭合，应使用新上游快照重新验收。

主要范围：`tools/CatalogImport`、`tools/IndustryImport/verify.py` 及其 fixture、目录清单、设备集成与包消费示例。新增一个可选数据文件，不自动同时打开两个文件，保持默认八文件预算。

## 5. N03：历史资源逐项追溯或替换

### 5.1 先形成资源台账

以项目实际 EmbeddedResource、DataLoader 和 CommonData 引用为准，逐项记录：资源文件、消费接口、当前覆盖、原始来源、固定版本、许可文件、转换规则、计数、状态。对运行中仍会读取和仍随包分发的资源都检查，避免只清理“新 API 没有调用”的旧文件。

每个资源只有在证据成立时选择以下路径：

1. **来源可核实**：补齐原始输入、固定版本、许可及转换说明。
2. **来源无法核实但有等价替代**：迁移到来源明确的数据，保留调用能力并同步测试、文档和重放版本。
3. **暂时没有合法且等价的替代**：列明具体接口、覆盖影响和阻塞原因；保持未闭合状态，不能以空列表、删除功能或编造真实映射宣称完成。

### 5.2 优先替代路线

|资源组|优先方案|必须保持的约束|
|女性名、姓氏|核对已固定 Faker 提交中的对应词表与许可后提取|性别/姓名组合、非空、格式和确定性|
|国家、城市、中国区划文本|从已核实 CLDR、GeoNames、中国区划快照确定性投影|实际父级、明确覆盖和语言；核心保持离线且不依赖 SQLite|
|职业、颜色、邮件域名|复用现有原创职业样本、已核对色表、示例域名规则；核对旧模型映射|旧入口可用，正常邮件采用示例域名，声明具体样本范围|
|中文字符集合|核实当前集合来源；无法补证时独立构建并标明模拟字符集合|正常输出不含孤立代理项，长度预算不变；不声称覆盖全部简体汉字|
|银行前缀、IBAN/BBAN、电话区号|逐类核对适用来源及再分发条件，优先保留经验证的格式规则|国家格式、校验位、覆盖错误；随机格式不能冒充真实银行/地区映射|

每批替换先验证直接消费者，再扩大到依赖的模板和行业包。对来源受限的资源允许阶段性阻塞，但 N03 只有在全部分发资源完成核实或合格替换后才关闭。

资源变化必须更新内置数据身份；生成算法变化按实际影响更新生成契约身份。旧重放明确拒绝不兼容版本，NuGet 包版本沿用既有约定。

交付：逐项资源台账、许可通知、可重复转换步骤、覆盖变化说明、消费者回归和迁移示例。

## 6. N04：大数据输入与远程 CI

### 6.1 推荐分发方式

推荐使用独立、版本化的离线目录压缩包，代码仓库保存 manifest、许可证说明、转换工具与小型测试 fixture。复用现有代码包/数据包分离结构，CI 在构建准备阶段取回固定数据，库运行时继续完全离线。

- 形成固定的输入包清单，记录数据版本、各文件字节数和校验值；复用已有 manifest 校验机制。
- 本地先支持从明确的压缩包路径恢复到干净目录；CI 再使用固定下载位置恢复同一包，缺文件、版本错误或校验失败均中止。
- 同时检查当前待上传历史中的大 blob；只在新提交里删除文件或写入 .gitignore，不能消除旧历史中的大 blob。先交付迁移清单和恢复验证结果，历史迁移另行执行。
- 若仓库已有可用 LFS 设施，可改用 LFS 并在 checkout 显式拉取；本方案默认采用独立数据包，避免同时维护两套主要分发路径。
- 远程可访问的数据地址与代码候选尚未就绪时，完成本地准备并记录外部阻塞。不能对旧远程提交运行 CI 后声称验证了当前未提交候选。

### 6.2 工作流及证据

1. 保留 Windows/Linux 矩阵，固定 SDK、依赖锁和官方 Schema 套件提交。
2. 增加数据恢复与完整性预检查，随后运行脚本失败处理、受影响目录检查、双资产测试、七包打包及隔离消费。
3. 测试和 Schema 报告使用统一、显式证据目录；工作流以 `always()` 上传已产生的 TRX、Schema 矩阵、电话覆盖、目录报告、包消费 evidence.json 和包哈希。
4. 故障发生在正式报告生成之前时仍保留阶段、错误与候选信息。两个 OS 的产物按平台区分，不覆盖。
5. 固定大数据输入单独保存；每次 job 只上传必要验证证据及需要审阅的代码包，避免重复上传整个数据快照。
6. 远程证据包含实际 Git SHA、数据版本集合、测试资产目标、SDK/运行时、工作流运行链接和两个平台结果。

本地干净目录恢复及隔离消费完成后，N04 的准备部分可记完成；远程实际运行部分保持单独状态，直到同一候选两平台结果产生。

## 7. 实施顺序、影响与验证

执行顺序：N01 → N02 → N03 → N04 本地交付准备 → 最终本地门禁；N04 远程运行等待所需代码和数据在远端可达。

|阶段|直接影响|先做的验证|扩大范围的条件|
|---|---|---|---|
|N01|电话寻址、元数据适配、可能的正则路径|具体反例与全规则固定矩阵，两套资产|修改通用正则时追加 AutoBuilder/Schema 回归|
|N02|目录派生、关系检查、数据打包|小 fixture、两快照全量关系与差集核对|目录挂载及设备包消费|
|N03|内嵌资源、数据加载、依赖模板及重放|逐组来源检查和直接消费者测试|数据身份或共享行为变化时追加依赖项目|
|N04|数据恢复、构建脚本、工作流|缺失/损坏输入、恢复、失败中止测试|干净目录双目标包消费及实际两平台运行|
|最终候选|本轮全部改动|一次完整 Release 双资产测试、官方矩阵、七包消费|只对新的可行动失败继续修复|

总体 RiskLevel：HIGH，主要来自数据替换和交付路径；每项实施前补充实际 ChangedFiles、PublicContracts、RuntimePaths、Providers、TFMs、BuildPackaging、AffectedDependents。主代理负责公共契约、兼容性及最终集成；独立的资源清点、确定性转换、测试矩阵或示例任务委派给 luna_worker，分配明确文件范围。

百万条日志、时间序列与未变化目录查询证据按影响复用。本方案没有新的吞吐/内存发布阈值；只有实际修改对应热点、分配或并发路径时，才重新执行相关万条诊断与一次百万条正式确认。

自动审查修复最多三轮；仅 OPEN_ACTIONABLE 进入修复。来源缺失、远程未运行及已接受边界单列，遵循 GOAL_RULES 的停止和无进展规则。
